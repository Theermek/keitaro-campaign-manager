# TASK: веб-обёртка над Keitaro

## Контекст
Keitaro — рекламный трекер (конструктор ссылок): редиректит пользователей по правилам
(потокам) и считает статистику переходов. Нужен сервис из двух частей поверх Keitaro API.

Скриншоты из ТЗ — в `docs/screenshots/`:
- `01-campaign-flows.webp` — кампания: URL кампании, Flow 1 (страна → google.com), Flow 2 (офферы с долями %);
- `02-api-keys.webp` — где в админке API-ключи и документация;
- `03-create-form.webp` — примерный интерфейс создавания (Name, Geo, Offer с автокомплитом, Create);
- `04-campaign-settings.webp` — настройки кампании: домен, группа, источник.

Документация API — в `docs/keitaro-api/` (сохранена вручную из админки).
Описание логики существующего редактора по видео — в `docs/editor-behavior.md`.

## Часть 1. Создаватор кампаний
Форма: название, гео-код страны (например AU), оффер (поиск с автокомплитом по офферам Keitaro).
Создаёт кампанию:
- настроены домен, группа и источник (значения — в `.env`/конфиге, ID получаем через API);
- Flow 1: фильтр «страна = указанное гео» → редирект на https://google.com;
- Flow 2: редирект на выбранный оффер.

## Часть 2. Редактор существующей кампании
- Выбор кампании, просмотр её потоков и офферов с долями.
- Добавление и удаление офферов в потоке.
- Логика и цифры (доли офферов) — как в существующем редакторе, см. `docs/editor-behavior.md`.

## Стек и сдача
- Backend: FastAPI + SQLAlchemy, миграции (Alembic).
- Frontend: простой (решить на этапе плана).
- README: установка, `.env`, миграции, запуск.

## Правила безопасности (обязательно)
- Keitaro общий и рабочий. Создавать, менять и удалять можно **только** кампании
  с префиксом `test_<фамилия>_`. Эта проверка должна быть и в коде (backend отклоняет
  операции над чужими кампаниями).
- Не трогать офферы, домены, группы, источники и чужие кампании — только чтение.
- Секреты (URL, API-ключ) — только в `.env`. Никогда не писать их в код, README, логи и коммиты.
- Любой изменяющий запрос к Keitaro API (POST/PUT/DELETE) выполнять только после моего подтверждения.

## Решения (заполнить после плана)
- Что храним в БД и зачем: `stream_offer` — снимок офферов потока (active/removed, pin, имя),
  т.к. Keitaro не хранит удалённые офферы и pin; `operation_log` — аудит изменяющих запросов.
  Кампании и потоки не храним — источник правды Keitaro. Draft — только на фронте.
- Фронт: Jinja2 + Alpine.js (CDN, без сборки). Подробно — `docs/PLAN.md`.
- Как пересчитываются доли офферов при добавлении/удалении: целые числа; `free = 100 − Σ pin`,
  каждому незакреплённому активному `free // n`, остаток — по +1 последним офферам; removed = 0%;
  при fetch не пересчитываем. Сортировка — по убыванию доли.
- Как задаются домен, группа, источник: по имени в `.env`, ID получаем через API.
